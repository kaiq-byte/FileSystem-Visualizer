sistemas de arquivos — do bloco cru ao ext4

O disco não sabe
o que é um arquivo.

Para o hardware, um HD ou SSD é um array gigante de blocos numerados, todos do mesmo tamanho. "Pasta" e "arquivo" não existem aí — são uma construção de software. Role para ver como o ext4 constrói essa ilusão em cima de dois comandos.

01 — o hardware

Só existem dois comandos.

Nem o controlador do disco, nem o sistema operacional antes de montar um filesystem, conhecem "arquivo". Existe um array numerado de blocos — geralmente 512 bytes ou 4096 bytes cada — e nada mais.

Todo bloco pode ser lido ou escrito, individualmente, por número.

02 — a instrução nativa

READ_BLOCK(N) e WRITE_BLOCK(N, dados).

É o vocabulário inteiro do hardware. A mesma lógica de LOAD/STORE que a CPU usa para endereçar a RAM — só que aqui o endereço é um bloco do disco, não uma posição de memória.

READ_BLOCK(42)
WRITE_BLOCK(42, dados)
03 — o problema real

Um arquivo raramente cabe em um bloco.

Um documento de 36 KB precisa de vários blocos — e o disco não tem obrigação nenhuma de colocá-los lado a lado. Eles podem cair em qualquer região livre, longe uns dos outros.

Sem um registro de quais blocos pertencem ao arquivo e em que ordem, os bytes recuperados viram ruído.

04 — a solução do ext4

Um registro fixo por arquivo: o inode.

O ext4 reserva, de antemão, uma região do disco só para metadados. Cada arquivo ganha um inode — uma entrada de tamanho fixo (256 bytes, tipicamente) guardada nessa tabela.

Na prática esse bloco é só bytes crus, mas o kernel os lê como uma struct ext4_inode: campos fixos, em offsets fixos. O inode não guarda o nome do arquivo — guarda quem é o dono, permissões, timestamps, tamanho — e, principalmente, onde estão os blocos de dados.

05 — extents, não ponteiros soltos

Em vez de um ponteiro por bloco, intervalos.

Ao invés de listar block 5312, depois 5313, depois 5314... o inode do ext4 guarda faixas contínuas: início + tamanho. Um arquivo espalhado em três regiões vira só três entradas — não centenas.

E como cada entrada é uma faixa matemática, calcular "onde está o byte 30000 deste arquivo" é aritmética direta — não uma travessia sequencial.

06 — diretório é arquivo

Uma pasta também tem um inode.

Um diretório é só um arquivo especial: seu conteúdo, guardado nos próprios blocos de dados, é um vetor de registros — struct ext4_dir_entry — e cada um desses registros é exatamente a relação nome ↔ inode.

documento.txt → inode 88 foto.jpg → inode 245 projetos/ → inode 12
07 — a travessia completa

Abrir "documento.txt" em quatro saltos.

O caminho não tem atalho: ler o bloco do diretório → achar a linha com o nome → seguir para o inode 88 → ler os extents → ler os blocos de dados de fato.

Cada seta nesse caminho é, no fundo, uma chamada READ_BLOCK.

08 — a rotina de um cd

cd /home/folder1: a mesma travessia, encadeada duas vezes.

O kernel resolve o caminho um componente por vez, e cada componente é a mesma dupla struct → struct que já vimos: primeiro acha o nome na tabela de diretório, depois lê o inode que ela aponta.

Para "/home/folder1" isso significa repetir o padrão duas vezes seguidas — uma para achar "home" dentro de "/", outra para achar "folder1" dentro de "home".

No fim, o processo não guarda um caminho de texto: guarda só o número do inode atual, o cwd.

a pilha inteira, de cima a baixo

ext4 é software. O hardware não sabe que ele existe.

FAT, ext4 e NTFS não são hardwares diferentes — são três implementações de software que resolvem o mesmo problema com estruturas de dados internas diferentes. Por isso o mesmo pendrive físico aceita ser formatado como qualquer um dos três: o disco só recebe READ_BLOCK / WRITE_BLOCK, seja qual for o "dicionário" por cima.

em resumo

Arquivo é uma ideia. Bloco é o fato físico.

O ext4 monta essa ideia com três peças: uma área reservada de inodes, um inode por arquivo guardando metadados e extents, e diretórios que são só arquivos cujo conteúdo mapeia nomes para números de inode.

Tudo isso roda como código comum — o file management system — dentro do sistema operacional. O disco, do começo ao fim, continua sem saber o que é um arquivo.
